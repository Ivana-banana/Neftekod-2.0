# CLAUDE.md — правила работы над проектом

Проект: мультиагентная система (МАС) для рекомендаций оператору по режиму цепочки
**АВТ → гидроочистка → блендинг** товарного дизельного топлива. Хакатон «Нефтекод 2.0».

Постановка — `tz_neftekod.md`, справочник тегов — `tags_hackathon.md`, схемы —
`avt_schemas.md`. Репозиторий: https://github.com/IR630/neftekod-2.0

## Как здесь выигрывают

Критерии оценки (`tz_neftekod.md`, §6): работа с данными, качество прогноза,
мультиагентность, оптимизация и безопасность, надёжность, объяснимость,
воспроизводимость, демонстрация. Целостный работающий прототип оценивается выше
набора несвязанных ноутбуков/моделей.

**Ключевой принцип задачи**: качество и жёсткие технологические ограничения имеют
приоритет над экономическим эффектом. Недопустимый режим нельзя «компенсировать»
более высокой производительностью или меньшими затратами — ни в модели, ни в коде.

На демонстрации нужно показать минимум 4 сценария: устойчивый период без лишних
действий; период с риском ухудшения качества; данные неполные/устаревшие/аномальные;
полный цикл агентов от входа до финальной рекомендации.

При дефиците времени порядок приоритета: (1) сквозной прогон данные→рекомендация
на одном сценарии, (2) жёсткие ограничения и тест на них, (3) остальные 3
демо-сценария, (4) объяснимость/визуализация — полировка UI откладывается
последней. Каждый сценарий прогоняется отдельным детерминированным скриптом
(фиксированный seed/frozen timestamp), вывод сохраняется; на случай сбоя на
сцене — записанный скринкаст последнего успешного прогона. Сценарии
фиксируются до финальной настройки моделей и не используются как критерий
донастройки гиперпараметров — иначе метрика на демо перестаёт что-либо
доказывать про остальные данные.

Сценарий, использующий синтетические/заглушечные входные данные вместо
реальных источников (например, блендинг без спецификации — см. ADR-004),
печатает в лог `[MOCKED: что и почему]` при запуске — не полагаться на устное
упоминание. В питче и README отдельно перечисляется, что не реализовано/не
проверено — это часть демонстрации, а не признание слабости.

## Неподвижные ограничения

- Жёсткие проверки не нарушаются никогда, даже ради лучшей метрики в другом месте:
  сера в товарном ДТ ≤ 10 мг/кг; доли компонентов блендинга = 100%; рекомендация не
  выходит за явно заданные технологические/модельные диапазоны.
- При нехватке данных или отсутствии допустимого варианта — явный отказ от
  рекомендации с объяснением причины, а не рискованная догадка.
- Python (`.py`/`.ipynb`); запуск воспроизводим по README (зависимости, структура,
  команда запуска) — это часть технических требований, а не опция.
- Train/test split — только по времени. Случайное перемешивание строк временного
  ряда, приводящее к утечке из будущего, — дефект, а не мелкая недоработка.
- Если для параметра нет подтверждённого рабочего диапазона — исторический
  min/max не выдаётся за промышленный предел; консервативный модельный диапазон
  явно помечается как допущение.

## Данные — известные ловушки (проверено в этом репозитории)

- `avt_tags.csv` / `242000_tags.csv` — 10-минутная телеметрия, 2023-01-01…2026-08-07,
  ~189k строк. Коды колонок 1:1 совпадают с листом «КИП» в `tags_hackathon.md`
  (сверено программно) — справочнику можно доверять.
- `lims_export_2023.xlsx` и `pak_export_2023.xlsx` — **не** простая таблица для
  `pd.read_excel()` (многоуровневый заголовок, у каждого показателя своя пара
  колонок с независимым охватом и частотой). Полный разбор формата и план
  парсера в единый long-format `(timestamp, tag, value, source)` — в
  `.claude/skills/parse-lims-pak/SKILL.md` (загружается по требованию, не
  дублировать сюда).
- Охват по времени сильно неравномерный, и это не баг экспорта — не
  интерполировать через многолетний пропуск; явно хранить возраст/доверие к
  каждому значению (требование ТЗ, §2). Конкретный пример разрыва — в skill выше.
- Единицы измерения — конвертации фиксировать явно и воспроизводимо; короткое имя
  тега само по себе не говорит о физическом смысле — смотреть `tags_hackathon.md`.

### Открытые вопросы к организаторам — не полагаться молча, пока нет ответа

Каждый пункт зафиксирован как ADR в `docs/adr/` (статус/контекст/решение/
последствия) и подтверждается ссылкой в коде на месте использования допущения
(`# см. ADR-00N`) — держать только в этом файле недостаточно, комментарий в
коде переживёт рефакторинг раздела.

- [ADR-001](docs/adr/001-mg-sulfur-q-tag.md) — тег `24-2000:Mg.Sulfur.Q` в
  справочнике «ПАК» vs `24-2000:Mg.Sulfur` (без `.Q`) в реальном файле
  `pak_export_2023.xlsx` — тот же это тег или нет.
- [ADR-002](docs/adr/002-vak-formulas.md) — формулы листа «ВАК» при прямой
  подстановке значений дают физически невозможные величины (например,
  `24-2000:GODT:T90` ≈ 166 тыс. вместо ожидаемых ~300–400 °C).
- [ADR-003](docs/adr/003-lims-pipeline-point.md) — `LIMS:24-2000.Pipeline.D15`
  и `LIMS:24-2000.Pipeline.95%.T` из формул ВАК ссылаются на точку отбора,
  которой в `lims_export_2023.xlsx` нет.
- [ADR-004](docs/adr/004-blending-data-absent.md) — материалов по блендингу
  (составы, рецептуры, спецификация товарного ДТ) в пакете нет — сценарий
  придётся делать модельным.
- [ADR-005](docs/adr/005-lims-unit-row-mismatch.md) — в блоке «АВТ. Точка
  отбора 1» файла `lims_export_2023.xlsx` строка единиц не соответствует
  показателям (`D15` — «°С», `50%.T` — «кг/м3»); плюс сера объявлена как
  `ppm` в ПАК и `мг/кг` в ЛИМС. Воспроизводится
  `neftekod.parse_lims_pak.unit_conflicts()`.

Принятые решения (не вопросы к организаторам):
[ADR-006](docs/adr/006-time-split.md) — точка отсечения train/test:
train ≤ 2025-12-24, зазор 7 суток, test с 2026-01-01. Зафиксирована до
обучения моделей и не подбирается по метрике.

## Мультиагентность

- Роли из `tz_neftekod.md`, §3: агент качества, агент надёжности, агент оптимизации,
  оркестратор. Число ролей не фиксировано, но взаимодействие между ними должно быть
  явно видно в коде и на демонстрации — не «один большой промпт с масками ролей».
- Каждая роль — отдельный subagent-файл со своим системным промптом и списком
  инструментов (`.claude/agents/quality.md`, `.claude/agents/reliability.md`,
  `.claude/agents/optimization.md`), а не ветка if/else внутри одного промпта —
  иначе «мультиагентность» на демо не отличить от одной модели с разными масками.
- Оркестратор разрешает конфликт целей и обязан уметь вернуть «нет допустимой
  рекомендации» вместо натягивания результата. Финальную рекомендацию он проверяет
  как adversarial-ревьюер: получает только (вход, рекомендация, применённые
  ограничения), не reasoning исполнителей. Не может независимо воспроизвести
  «ограничения соблюдены» — рекомендация отклоняется, а не пропускается с оговоркой.

## Тесты и доказательство результата

- Парсер lims/pak (нетривиальные заголовки) закрывается тестом на реальном фрагменте
  файла, не только на синтетике.
- Time-based split сам по себе не ловит утечку внутри признака: каждая фича
  временного ряда фиксирует явную точку отсечки (cutoff), и тест
  `test_no_feature_leakage` проверяет, что ни одна фича не использует значения
  с `timestamp > prediction_time`.
- Синхронизация источников по времени (не по номеру строки, §2 ТЗ) — отдельный тест:
  разная частота/охват источников не должна давать ложный merge.
- Жёсткие ограничения (сера ≤10 мг/кг, сумма долей = 100%) закреплены тестом навсегда
  — это прямые баллы по критерию «Оптимизация и безопасность».
- «Должно работать» не считается результатом: сквозной прогон «данные → оценки
  агентов → рекомендация» — обязательная проверка перед демонстрацией.

## Верификация и честность (симулятора для проверки эффекта нет)

- Организаторы не выдают симулятор для проверки последствий рекомендаций — вопрос
  открыт (см. переписку с оргами), но по тексту ТЗ (§6) допустима «модельная оценка»
  при явной оговорке допущений.
- Два разных числа нельзя путать: (1) качество прогноза на отложенной по времени
  истории — проверяемо честно; (2) оценка эффекта ещё не случавшегося управляющего
  действия — по построению не подтверждена историей. В коде и в отчёте оба явно
  подписаны: что каждое из них доказывает и чего не доказывает.
- Рекомендация, вышедшая за пределы обучающего диапазона по входам, помечается как
  «вне диапазона обучения» — агент не должен тихо экстраполировать с той же
  уверенностью, что и внутри диапазона.
- Это разделение — не только проза в отчёте: каждый вывод агента-оптимизации несёт
  машиночитаемое поле `evidence_type: backtested | simulated_unvalidated`, и тест
  в CI проверяет, что поле не пропущено ни у одного вывода.

## Работа с ИИ-ассистентом (Claude Code)

- Жёсткие ограничения проверяются не только текстом правила, но и Stop hook:
  перед тем как ход агента-оптимизатора считается завершённым, хук в
  `.claude/hooks/` прогоняет `tests/test_hard_constraints.py` (пока файла нет —
  хук молча пропускает, начнёт действовать сам, как только тест появится). Хук
  нельзя обойти формулировкой в чате, в отличие от текста в этом файле.
- Ни один агент и ни один раздел отчёта не пишет «проверено»/«работает» без
  прикреплённого вывода команды-проверки (текст теста, код возврата, число
  прошедших/упавших кейсов). Утверждение без прикреплённой команды — брак,
  а не допустимое сокращение пути.
- Раз в несколько коммитов: попросить Claude пересказать правила этого файла
  своими словами. Пропущенное правило — сигнал вынести раздел в skill
  (`.claude/skills/`) или per-directory `CLAUDE.md`, а не подчёркивать
  существующий текст ещё сильнее.

## Git

- Крупные CSV (`data/avt_tags.csv` 247 МБ, `data/242000_tags.csv` 91 МБ) не
  коммитятся — ссылка на Google Drive в README.md, `.gitignore` уже настроен.
- Синхронизация перед началом работы и перед коммитом: `git fetch --prune && git status -sb`.
- Коммит после каждого законченного логического шага; историю `master` не переписывать.
