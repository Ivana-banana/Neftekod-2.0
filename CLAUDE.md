# CLAUDE.md — правила работы над проектом

Проект: мультиагентная система (МАС) для рекомендаций оператору по режиму цепочки
**АВТ → гидроочистка → блендинг** товарного дизельного топлива. Хакатон «Нефтекод 2.0».

Постановка — `docs/tz/tz_neftekod.md`, справочник тегов — `docs/tz/tags_hackathon.md`, схемы —
`docs/tz/avt_schemas.md`. Репозиторий: https://github.com/IR630/neftekod-2.0

## Как здесь выигрывают

Критерии оценки (`docs/tz/tz_neftekod.md`, §6): работа с данными, качество прогноза,
мультиагентность, оптимизация и безопасность, надёжность, объяснимость,
воспроизводимость, демонстрация. Целостный работающий прототип оценивается выше
набора несвязанных ноутбуков/моделей.

**Ключевой принцип задачи**: качество и жёсткие технологические ограничения имеют
приоритет над экономическим эффектом. Недопустимый режим нельзя «компенсировать»
более высокой производительностью или меньшими затратами — ни в модели, ни в коде.

На демонстрации нужно показать минимум 4 сценария: устойчивый период без лишних
действий; период с риском ухудшения качества; данные неполные/устаревшие/аномальные;
полный цикл агентов от входа до финальной рекомендации.

При дефиците времени порядок приоритета: (1) сквозной прогон данные→рекомендация
на одном сценарии, (2) жёсткие ограничения и тест на них, (3) остальные 3
демо-сценария, (4) объяснимость/визуализация — полировка UI откладывается
последней. Каждый сценарий прогоняется отдельным детерминированным скриптом
(фиксированный seed/frozen timestamp), вывод сохраняется; на случай сбоя на
сцене — записанный скринкаст последнего успешного прогона. Сценарии
фиксируются до финальной настройки моделей и не используются как критерий
донастройки гиперпараметров — иначе метрика на демо перестаёт что-либо
доказывать про остальные данные.

Сценарий, использующий синтетические/заглушечные входные данные вместо
реальных источников (например, блендинг без спецификации — см. ADR-004),
печатает в лог `[MOCKED: что и почему]` при запуске — не полагаться на устное
упоминание. В питче и README отдельно перечисляется, что не реализовано/не
проверено — это часть демонстрации, а не признание слабости.

## Среда развёртывания — закрытый контур

Организаторы на Q&A 2026-09-11 ([разбор](docs/tz/qa-session-2026-09-11.md), A1–A4):
технологическая сеть **не связана с внешним интернетом**, решение должно
работать локально. Внутри контура есть локальная LLM с OpenAI-совместимым API,
потолок — порядок **30 млрд параметров**. Оценивается «архитектурная
грамотность системы и возможность запуска в закрытой среде».

- Никаких обращений к внешним API в коде решения. Зависимость, которая тянется
  в интернет на рантайме, — дефект развёртывания, а не деталь реализации.
- LLM не обязана быть в каждом агенте: организаторы прямо сказали, что
  инженерные и физико-химические модели приветствуются, если обоснованы (A3).
  Числа считают детерминированные модули, роли их вызывают и проверяют —
  это подтверждённый выбор, а не упрощение.
- Чистый Python без фреймворка оркестрации выбран осознанно: система —
  фиксированный конвейер «качество → надёжность → оптимизация → оркестратор»,
  а это тот случай, где обзор
  ([docs/research/2026-09-agent-frameworks.md](docs/research/2026-09-agent-frameworks.md))
  считает чистый Python уместным. Довод нужен на защите, его стоит помнить.

## Неподвижные ограничения

- Жёсткие проверки не нарушаются никогда, даже ради лучшей метрики в другом месте.
  Организаторы назвали обязательными **три** показателя товарного ДТ
  ([ADR-015](docs/adr/015-spec-t95-cetane.md)): сера ≤ 10 мг/кг, T95 ≤ 360 °C,
  цетановое число ≥ 51. К ним добавлена плотность 820–845 кг/м³
  ([ADR-016](docs/adr/016-density-spec.md)) — нормируемый ГОСТ показатель на той
  же точке отбора, который на реальных данных нарушается. Плюс доли компонентов
  блендинга = 100% и выход рекомендации за явно заданные технологические и
  модельные диапазоны. Запас по одному показателю не покупает нарушение по
  другому.
- Предел серы задан организаторами; численные пределы T95 и цетанового числа они
  оставили команде, и в коде, карточке и отчёте они подписаны как параметры
  сценария по ГОСТ, а не как подтверждённый норматив. Это разные по статусу
  числа, и смешивать их нельзя.
- **Пределы ГОСТ зависят от климатического сорта**, а не абсолютны
  ([разбор ГОСТ Р 52368](docs/research/2026-09-gost-r-52368-dt.md)): для
  летнего/межсезонного ряда (табл. 2–3) T95 ≤ 360 °C и ЦЧ ≥ 51, а для зимних и
  арктического классов (табл. 4) — отгон ≥ 95 % до 340 °C, то есть T95 ≤ 340 °C,
  и ЦЧ 49/49/48/47/47. Взять «360 и 51» как универсальную норму — ошибка.
  На наших данных сорт подтверждён измерением: CFPP `Гидроочистка.2` в 2026 году
  лежит в −16…0 °C при требовании ≤ −20 °C для зимних классов, то есть
  выпускается летнее/межсезонное топливо и применяется табл. 2. Проверять это
  заново при смене окна сценария, а не считать раз и навсегда.
- Показатель, не подтверждённый анализом свежее своего порога, не считается
  выполненным: «не измерили» ≠ «в пределах нормы». Пороги устаревания разные,
  потому что разная частота отбора (T95 — 48 ч, цетановое число — 42 суток).
- «Не подтверждён» ≠ «нарушен» ([ADR-017](docs/adr/017-unverified-vs-violated.md)):
  доказанное нарушение блокирует всё, включая сохранение режима;
  неподтверждённый показатель блокирует любое изменение режима или состава, но
  допускает `hold` с явным `unverified_spec_indicators`. С пределом сравнивается
  значение в разрешении лабораторного входа (T95 и вспышка — 1 °C, плотность и
  ЦЧ — 0.1): превышение меньше половины шага данные не различают. Сера не
  округляется.
- При нехватке данных или отсутствии допустимого варианта — явный отказ от
  рекомендации с объяснением причины, а не рискованная догадка.
- Python (`.py`/`.ipynb`); запуск воспроизводим по README (зависимости, структура,
  команда запуска) — это часть технических требований, а не опция.
- Train/test split — только по времени. Случайное перемешивание строк временного
  ряда, приводящее к утечке из будущего, — дефект, а не мелкая недоработка.
- Если для параметра нет подтверждённого рабочего диапазона — исторический
  min/max не выдаётся за промышленный предел; консервативный модельный диапазон
  явно помечается как допущение.

## Данные — известные ловушки (проверено в этом репозитории)

- `avt_tags.csv` / `242000_tags.csv` — 10-минутная телеметрия, 2023-01-01…2026-08-07,
  ~189k строк. Коды колонок 1:1 совпадают с листом «КИП» в `docs/tz/tags_hackathon.md`
  (сверено программно) — справочнику можно доверять.
- `lims_export_2023.xlsx` и `pak_export_2023.xlsx` — **не** простая таблица для
  `pd.read_excel()` (многоуровневый заголовок, у каждого показателя своя пара
  колонок с независимым охватом и частотой). Полный разбор формата и план
  парсера в единый long-format `(timestamp, tag, value, source)` — в
  `.claude/skills/parse-lims-pak/SKILL.md` (загружается по требованию, не
  дублировать сюда).
- Охват по времени сильно неравномерный, и это не баг экспорта — не
  интерполировать через многолетний пропуск; явно хранить возраст/доверие к
  каждому значению (требование ТЗ, §2). Конкретный пример разрыва — в skill выше.
- Единицы измерения — конвертации фиксировать явно и воспроизводимо; короткое имя
  тега само по себе не говорит о физическом смысле — смотреть `docs/tz/tags_hackathon.md`.
  Это подтверждено первичным источником: на [схемах АВТ с позициями](docs/tz/avt_schema_positions.md)
  коды `T74`, `T66`, `T24`, `T48`, `T42` проставлены у приборов **PI**, то есть
  это давления, а не температуры. Префикс кода не означает физическую величину.
- На точке товарного продукта `Гидроочистка.2` ЛИМС измеряет **семь** нормируемых
  ГОСТ показателей: `Mg.Sulfur`, `95%.T`, `CetaneNumber`, `FlashPoint`, `D15`,
  `I250`, `I350`. Последние четыре — это температура вспышки (К5: выше 55 °C),
  плотность при 15 °C (820,0–845,0 кг/м³) и отгон при 250 °C (< 65 % об.) и при
  350 °C (≥ 85 % об.). Отсутствие проверки по ним — незакрытая работа, а не
  отсутствие данных.
- Чего для полного ГОСТ действительно нет в пакете: `T10` разгонки (без неё не
  считается цетановый индекс ≥ 46), вязкость при 40 °C, полициклическая
  ароматика, вода, зольность, коксуемость, HFRR, FAME. `T50`, `T90` и конец
  кипения ГОСТ отдельными пределами **не** нормирует — они нужны только для
  расчёта цетанового индекса, и требовать по ним «соответствия» неверно.
- Материальный баланс приборами обеспечен, вопреки прежней формулировке в
  README: на 24-2000 есть `F17`/`T23` (расход гидроочищенного ДТ с установки) и
  `T11`/`F26` (расход сырья), на АВТ — суммарный расход нефти и расходомеры на
  всех выводах фракций. Ограничение не в отсутствии данных, а в отсутствии
  единиц (ADR-007): выпуск считается только в относительных величинах.
  Энергопотребление прямыми тегами не покрыто — только прокси (ВСГ `P24`,
  расходы пара).

### Ответы организаторов и оставшиеся вопросы

Приоритетный источник уточнений — [ответы, зафиксированные 2026-09-10](docs/tz/organizer-clarifications.md).
Исходные XLSX не менялись; пайплайн применяет поправки формул и единиц,
сохраняет их происхождение и добавляет время доступности анализов.

- Сопоставление CSV ↔ КИП подтверждено. Для гидроочистки управления:
  `P8` — температура ГСС на входе Р-202, `T11` — массовый расход сырья,
  `F19` — давление на входе. Единицы/масштабы КИП не уточнены; аномалии
  сигналов остаются открытыми (ADR-007), но прежний вывод о доказанно неверном
  справочнике отменён. **Схемы АВТ с позициями получены 2026-09-14** —
  [разбор](docs/tz/avt_schema_positions.md). Они покрывают только АВТ: 24-2000 к
  ним не относится по прямому ответу организаторов, поэтому единицы `P8`/`T11`/`F19`
  ими не закрываются.
- Ошибка строки единиц ЛИМС подтверждена (ADR-005): нормализовать по показателю,
  сохраняя `unit_declared`. Сера ПАК соответствует «Гидроочистка.2»,
  1 ppm = 1 мг/кг; суффикс `.Q` отдельно не объяснён (ADR-001).
- Организаторы исправили T90, T50, CloudPoint, CFPP, T95 гидроочистки и скобки
  CFPP АВТ (ADR-002). Использовать формулы из уточнений; их точность ещё
  проверять. Соответствие `Pipeline` точке ЛИМС не дано (ADR-003).
- Точки отбора ЛИМС нумеруются по удалённости от начала процесса, а не по
  времени. Для 24-2000 подтверждено прямо: точки «перед установкой» и «после
  установки», то есть `Гидроочистка.1` — сырьё, `Гидроочистка.2` — продукт
  ([Q&A](docs/tz/qa-session-2026-09-11.md), A5). Допущение ADR-013 и ADR-015
  теперь опирается на слова организаторов, а не только на нашу интерпретацию.
- Время ЛИМС — отбор, публикация до 4 часов позже. Без фактической публикации
  принимать доступность признака с `sample_time + 4h`; лабораторная цель
  относится ко времени отбора. Все источники в одном, не названном часовом поясе.
- Блендинг официально модельный, дополнительных данных не будет (ADR-004).
  Обязательны сера, T95, цетановое число; численные пределы последних двух
  задаются допущениями. Тонна присадки стоит 100 тонн ДТ; смысл «до 3%» и
  зависимость эффекта от дозы не определены.
- Шаг рекомендаций 15–60 минут, горизонт и технологические лаги 0–3 часа.
  Ограничений скорости изменения в задаче не задано, ограничения диапазонов
  остаются. Лаги выбирать только по train/validation.
- Команда строит свою модель и несколько изменяемых сценариев; результаты
  должны зависеть от свойств сырья и задания качества продукта.

## Мультиагентность

- Роли из `docs/tz/tz_neftekod.md`, §3: агент качества, агент надёжности, агент оптимизации,
  оркестратор. Число ролей не фиксировано, но взаимодействие между ними должно быть
  явно видно в коде и на демонстрации — не «один большой промпт с масками ролей».
- Каждая роль — отдельный subagent-файл со своим системным промптом и списком
  инструментов (`.claude/agents/quality.md`, `.claude/agents/reliability.md`,
  `.claude/agents/optimization.md`), а не ветка if/else внутри одного промпта —
  иначе «мультиагентность» на демо не отличить от одной модели с разными масками.
- Оркестратор разрешает конфликт целей и обязан уметь вернуть «нет допустимой
  рекомендации» вместо натягивания результата. Финальную рекомендацию он проверяет
  как adversarial-ревьюер: получает только (вход, рекомендация, применённые
  ограничения), не reasoning исполнителей. Не может независимо воспроизвести
  «ограничения соблюдены» — рекомендация отклоняется, а не пропускается с оговоркой.

## Тесты и доказательство результата

- Парсер lims/pak (нетривиальные заголовки) закрывается тестом на реальном фрагменте
  файла, не только на синтетике.
- Time-based split сам по себе не ловит утечку внутри признака: каждая фича
  временного ряда фиксирует явную точку отсечки (cutoff), и тест
  `test_no_feature_leakage` проверяет, что ни одна фича не использует значения
  с `timestamp > prediction_time`.
- Синхронизация источников по времени (не по номеру строки, §2 ТЗ) — отдельный тест:
  разная частота/охват источников не должна давать ложный merge.
- Жёсткие ограничения (сера ≤ 10 мг/кг, T95 ≤ 360 °C, цетановое число ≥ 51,
  плотность 820–845 кг/м³, сумма долей = 100%) закреплены тестом навсегда — это прямые баллы по критерию
  «Оптимизация и безопасность». Отсутствие показателя в рекомендации — тоже
  нарушение: иначе проверку можно обойти, просто не положив число в пакет.
- Модель смешения, форма которой не подтверждена, не выбирается по удобству: при
  двух рассматриваемых формах берётся худшая (ADR-015 — нелинейный blend index
  для цетанового числа измеренно лежит выше линейного среднего, то есть сам по
  себе не консервативен).
- «Должно работать» не считается результатом: сквозной прогон «данные → оценки
  агентов → рекомендация» — обязательная проверка перед демонстрацией.

## Верификация и честность (симулятора для проверки эффекта нет)

- Организаторы поручили команде использовать собственную обоснованную модель
  (допустима линейная) и несколько изменяемых сценариев. Разделение проверки
  прогноза на истории и модельной оценки действий прямо разрешено ответом.
- Два разных числа нельзя путать: (1) качество прогноза на отложенной по времени
  истории — проверяемо честно; (2) оценка эффекта ещё не случавшегося управляющего
  действия — по построению не подтверждена историей. В коде и в отчёте оба явно
  подписаны: что каждое из них доказывает и чего не доказывает.
- Рекомендация, вышедшая за пределы обучающего диапазона по входам, помечается как
  «вне диапазона обучения» — агент не должен тихо экстраполировать с той же
  уверенностью, что и внутри диапазона.
- Это разделение — не только проза в отчёте: каждый вывод агента-оптимизации несёт
  машиночитаемое поле `evidence_type: backtested | simulated_unvalidated`, и тест
  в CI проверяет, что поле не пропущено ни у одного вывода.
- Разделение совпадает со стандартом отчётности из литературы по offline policy
  evaluation ([разбор](docs/research/2026-09-offline-policy-evaluation.md)):
  **блок A** — подтверждаемая предиктивная валидность на наблюдаемом мире
  (RMSE/MAE/R², holdout по времени); **блок B** — контрфактическая оценка
  политики, условная на предположениях (overlap, effective sample size, доля
  решений вне support, чувствительность к скрытому смешению). Объединять их в
  один «показатель точности модели» нельзя: почти идеальный прогноз факта
  совместим с полностью неидентифицируемым эффектом действия.
- Почему эффект уставок не идентифицируется именно у нас: организаторы
  подтвердили, что на АВТ и на 24-2000 работают АСУ с обратной связью
  ([Q&A](docs/tz/qa-session-2026-09-11.md), A7). Если регулятор почти
  детерминированно выбирает действие по состоянию, альтернативных действий в
  том же состоянии в истории почти нет, и объём архива причинного overlap не
  создаёт. Отказ сертифицировать изменение уставок — свойство данных, а не
  осторожность; на защите это формулируется именно так.

## Работа с ИИ-ассистентом (Claude Code)

- Жёсткие ограничения проверяются не только текстом правила, но и Stop hook:
  перед тем как ход агента-оптимизатора считается завершённым, хук в
  `.claude/hooks/` прогоняет `tests/test_hard_constraints.py` (пока файла нет —
  хук молча пропускает, начнёт действовать сам, как только тест появится). Хук
  нельзя обойти формулировкой в чате, в отличие от текста в этом файле.
- Ни один агент и ни один раздел отчёта не пишет «проверено»/«работает» без
  прикреплённого вывода команды-проверки (текст теста, код возврата, число
  прошедших/упавших кейсов). Утверждение без прикреплённой команды — брак,
  а не допустимое сокращение пути.
- Раз в несколько коммитов: попросить Claude пересказать правила этого файла
  своими словами. Пропущенное правило — сигнал вынести раздел в skill

## Git

- Крупные CSV (`data/avt_tags.csv` 247 МБ, `data/242000_tags.csv` 91 МБ) не
  коммитятся — ссылка на Google Drive в README.md, `.gitignore` уже настроен.
- Синхронизация перед началом работы и перед коммитом: `git fetch --prune && git status -sb`.
- Коммит после каждого законченного логического шага; историю `master` не переписывать.
- **Коммит выполняется автоматически, разрешение не спрашивается** — как и push
  (следующий пункт). Разрешения заданы в `.claude/settings.json`
  (`permissions.allow`); там же `permissions.deny` закрывает force-push,
  `rebase`, `commit --amend`, `reset --hard` и удаление веток — то, что
  переписывает уже отправленное.
- **Push выполняется автоматически, разрешение не спрашивается.** После
  каждого коммита — `git push`; репозиторий приватный, команда работает по
  нему же, и коммиты, лежащие только на ноутбуке, для остальных не
  существуют. Это постоянное разрешение на весь проект, а не на одну сессию.
- Автоматический push распространяется только на обычный `git push` в
  `master`. `--force`, `--force-with-lease`, `push` после `rebase`/`amend`
  уже отправленных коммитов и удаление веток остаются под явный запрос —
  они переписывают то, что другие могли забрать.
- Если push отклонён (не fast-forward), правило не отменяется: `git fetch`,
  разобраться с расхождением, сообщить о нём — а не оставлять коммиты
  локально молча.
