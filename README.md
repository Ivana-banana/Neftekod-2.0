# Нефтекод 2.0

Материалы хакатона: техническое задание, справочные данные и технологические схемы для задачи о мультиагентной системе управления цепочкой АВТ → гидроочистка → блендинг товарного дизельного топлива.

## Как запустить подготовительный пайплайн

Нужен Python ≥ 3.11. Из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
python scripts/prepare_data.py
pytest -q
```

`scripts/prepare_data.py` — одна команда от исходных выгрузок до готового
датасета. Он ничего не скачивает и не меняет исходные файлы; результат
детерминирован. В `build/` появляются:

| Файл | Что внутри |
|---|---|
| `lims_pak_long.csv` | ЛИМС + ПАК в едином long-format: исходные поля плюс `unit, unit_basis, available_at, availability_basis` (301 910 значений, 56 показателей). |
| `tag_map.csv` | Листы КИП+ЛА+ПАК+ВАК (172 записи); для ВАК — действующая формула, оригинал, источник поправки и статус проверки. |
| `coverage_report.csv` / `.md` | Покрытие и актуальность каждого показателя: первая/последняя дата, число значений, медианный интервал, максимальный разрыв. |
| `unit_conflicts.csv` | Исходные расхождения единиц рядом с нормализованными единицами и основанием исправления (ADR-005). |

Телеметрия (`data/*.csv`) для пайплайна не обязательна: без неё шаг сверки
колонок со справочником пишет предупреждение, остальные шаги отрабатывают.
Тесты, которым нужны эти файлы, при их отсутствии помечаются как skipped.

Зависимости описаны в `pyproject.toml` (не `requirements.txt`): `pip install -e`
одной командой ставит их и делает пакет `src/neftekod` импортируемым — иначе
скриптам и тестам понадобились бы правки `sys.path`.

В build/forecast_report.csv и build/forecast_report.md сохраняется backtest
прогноза серы для горизонтов 0–3 часа: persistence сравнивается с Ridge-моделью
на признаках ЛИМС/ПАК и телеметрии 24-2000 (P8, T11, F19). Синхронизация
выполняется по времени выдачи прогноза, а не по номеру строки. Для телеметрии
проверяются лаги 0, 1, 2 и 3 часа; выбор лага и alpha выполняется только на
fit/valid, test получает только выбранную комбинацию. Результаты разделены на
fit/valid/test.

Оценка запускается после подготовки данных:

    python scripts/evaluate_forecast.py

Лаг телеметрии и Ridge alpha выбираются на valid после обучения кандидатов на
fit; итоговая модель обучается на fit+valid и один раз проверяется на test.
Каждый результат помечен evidence_type: backtested. Это проверка качества
прогноза на истории, а не подтверждение эффекта будущего управляющего
воздействия.

### Синхронизация телеметрии

Модуль src/neftekod/features.py для каждого issue_time выбирает последнее
конечное измерение с timestamp <= issue_time - lag. Возраст измерения от
момента выдачи сохраняется в часах; длинные пропуски не интерполируются.
ЛИМС и ПАК допускаются в признаки только при одновременном выполнении
timestamp <= issue_time и available_at <= issue_time. На точной границе
доступности значение разрешено.

Единицы и физический масштаб P8, T11, F19 организаторами не сообщены.
Сырые значения не называются градусами, т/ч или МПа: Ridge использует их как
числовые сигналы и стандартизирует параметры только на fit. Это модельное
допущение (см. ADR-009), а не подтверждённая физическая интерпретация.
**Расчёт** T95 по формуле ВАК и точка `Pipeline` остаются заблокированными
согласно ADR-003. На само T95 это не распространяется: показатель измеряется
в ЛИМС на точке «Гидроочистка.2» — там же, где сера товарного продукта, — и
используется измерением, а не расчётом ([ADR-015](docs/adr/015-spec-t95-cetane.md)).

Baseline прогноза серы — **сдвинутый persistence**: `0.3 · последний
опубликованный анализ + 0.7 · уровень обучающей выборки`. Доля сдвига выбрана
только на valid, проверена на test один раз ([ADR-012](docs/adr/012-forecast-baseline.md)).
На test (горизонты 0–3 ч) RMSE 2.2955 / 2.3788 / 2.4088 / 2.3708 при
положительном R² на всех четырёх горизонтах; прежний persistence даёт
2.6203 / 2.8562 / 2.9211 / 2.7618 и отрицательный R², константа — 2.483.
Телеметрическая Ridge проигрывает разгромно (168.2206 / 143.1039 / 213.7566 /
254.4563) — это результат backtest, а не основание считать телеметрию
бесполезной: в данных есть редкие выбросы ЛИМС и поздний участок телеметрии с
большими возрастами признаков. Маркер 307.0 у `F19` причиной не оказался:
после маскирования дефектов телеметрии ([ADR-018](docs/adr/018-telemetry-defects.md))
метрики не изменились, потому что за время серии 307.0 не было ни одного анализа ЛИМС.

Причина, по которой свежий анализ входит в прогноз лишь на 30 %, названа
числом: корреляция соседних лабораторных анализов на fit равна −0.004.
На суточном шаге ряд ведёт себя как шум вокруг устойчивого уровня.

## Как запустить все четыре сценария

Сквозной прогон «данные → оценки агентов → рекомендация» одной командой:

    python scripts/run_all_scenarios.py

Нужны `build/lims_pak_long.csv`, `build/forecast_report.csv` (то есть сначала
`prepare_data.py` и `evaluate_forecast.py`) и телеметрия `data/242000_tags.csv`.
Если чего-то нет, скрипт называет недостающий файл и выходит с кодом 1.

Сводка последнего прогона (2026-09-16, после [ADR-018](docs/adr/018-telemetry-defects.md);
два запуска подряд, `md5sum -c` — 28/28 OK):

```
  сценарий      момент выдачи        риск качества  запас, мг/кг  severity  кандидатов  допустимых  рекомендация  вердикт
  ------------  -------------------  -------------  ------------  --------  ----------  ----------  ------------  ----------------------------
  stable        2026-02-04 12:00:00  high           1.46          0.045     12          1           hold          approved
  quality_risk  2026-05-12 14:00:00  high           1.01          0.124     12          1           hold          approved
  stale_data    2026-06-25 09:00:00  отказ          —             1.000     0           0           —             no_admissible_recommendation
  full_cycle    2026-04-04 20:00:00  high           2.33          0.068     12          1           hold          approved
```

Каждый сценарий можно прогнать отдельным скриптом:

| Сценарий | Скрипт | Окно и критерий отбора |
|---|---|---|
| 1 — устойчивый период | `scripts/scenario_stable.py` | самая спокойная неделя test-периода (ADR-010) |
| 2 — риск ухудшения качества | `scripts/scenario_quality_risk.py` | максимальный рост серы за 72 ч внутри полосы p05–p95 (ADR-011) |
| 3 — неполные и устаревшие данные | `scripts/scenario_stale_data.py` | середина крупнейшего разрыва публикации ЛИМС, 350 ч (ADR-011) |
| 4 — полный цикл агентов | `scripts/scenario_full_cycle.py` | наибольший запас по сере внутри полосы при допустимом режиме (ADR-011) |

Окна и моменты выдачи заморожены **до** правки моделей и закрыты тестом
`tests/test_scenarios.py`: поменять окно нельзя, не поменяв ADR. Случайности в
прогоне нет, поэтому два запуска подряд дают побайтово одинаковые файлы:

    python scripts/run_all_scenarios.py && md5sum build/scenario_*/* > /tmp/run1.md5
    python scripts/run_all_scenarios.py && md5sum -c /tmp/run1.md5

В каждом `build/scenario_*/` появляются:

| Файл | Что внутри |
|---|---|
| `context.json` | Вход сценария as-of: снимок ЛИМС/ПАК/телеметрии с возрастом каждого значения, диапазоны обучающей выборки, метрики backtest. |
| `quality.json` | Агент качества: прогноз серы, запас до предела в единицах backtest-RMSE, класс риска, флаг «вне диапазона обучения», доверие к входу, измеренные T95 и цетановое число с их свежестью (`spec_indicators`). |
| `reliability.json` | Агент надёжности: индекс тяжести режима по прокси, факторы риска, границы для оптимизации и перечень допущений прокси. |
| `optimization.json` | Кандидатные воздействия с `evidence_type` у каждого, причина отклонения каждого недопустимого, правила выбора, вход блендинга. |
| `submission.json` | Ровно то, что видит оркестратор: вход, рекомендация, применённые ограничения. Без reasoning исполнителей. |
| `decision.json` | Вердикт оркестратора, независимо воспроизведённые проверки, предупреждения либо причина отказа, и `limits` — чего проверка не доказывает. |
| `recommendation.md` | Карточка оператора по семи блокам ТЗ §5: состояние → риск → действие → эффект → проверка ограничений → уверенность → объяснение выбора. |

Каждую роль можно прогнать отдельно — так её запускает соответствующий
subagent из `.claude/agents/`:

    python scripts/scenario_stable.py --role quality

Роль считает и своих предшественников, но записывает только свой файл.

Состав блендинга модельный: рецептур и спецификации в пакете нет (ADR-004),
поэтому скрипт печатает `[MOCKED: …]` при запуске и повторяет пометку в
карточке. Сера дешёвого компонента при этом **измеренная** — берётся из анализа
`LIMS:Гидроочистка.1.Mass.Sulfur` с порогом устаревания 31 сутки
([ADR-013](docs/adr/013-blending-space.md)); его T95 — из
`LIMS:Гидроочистка.1.95%.T` ([ADR-015](docs/adr/015-spec-t95-cetane.md)). Из
модельных величин остаются доли компонентов, относительная цена и цетановое
число дешёвого компонента: оно не измеряется нигде в пакете. Правила решения
агентов и все пороги — [ADR-010](docs/adr/010-agent-decision-rules.md).

### Что сценарии доказывают, а что нет

На всех четырёх окнах система либо сохраняет режим, либо отказывается: ни одно
изменение уставок и ни одно изменение состава не проходит проверку. Причины
разные и названы машиночитаемыми кодами:

- `unvalidated_effect_model` — модель эффекта уставок (Ridge по телеметрии)
  проиграла baseline на отложенной истории, поэтому её прогноз не является
  основанием для действия;
- `insufficient_margin` — запас по сере меньше backtest-RMSE прогноза
  (2.409 мг/кг на худшем горизонте): заявленный выигрыш лежит внутри
  собственной ошибки. На 198 моментах test-периода с допустимым режимом
  медианный запас — 1.37 мг/кг;
- `unmodelled_spec_effect` — влияние изменения уставки на T95 и цетановое
  число не моделируется, поэтому обязательные показатели после действия
  неизвестны и действие не сертифицируется ([ADR-015](docs/adr/015-spec-t95-cetane.md));
- `unverified_spec_indicator` — обязательный показатель не подтверждён свежим
  анализом, поэтому любое изменение режима или состава не сертифицируется
  ([ADR-017](docs/adr/017-unverified-vs-violated.md));
- отказ по данным — последний анализ старше 48 ч (сценарий 3).

**Прогон 2026-09-15 после ADR-017.** Три сценария дают утверждённый `hold`,
у каждого с машиночитаемой пометкой `unverified_spec_indicators` и
предупреждением оркестратора:

| Сценарий | Вердикт | Не подтверждено | Числа |
|---|---|---|---|
| 1 — устойчивый | `hold`, approved | плотность продукта | анализу `D15` 50.0 ч при пороге 48; S = 9.298, T95 = 345.0, ЦЧ = 52.9 |
| 2 — риск качества | `hold`, approved | цетановое число продукта | анализу 61.2 сут при пороге 42; риск по сере `high` остаётся в предупреждении |
| 3 — устаревшие данные | `no_admissible_recommendation` | сера | последний анализ ЛИМС 179 ч при пороге 48 — отказ агента качества, как и задумано |
| 4 — полный цикл | `hold`, approved | плотность **дешёвого компонента** | плотность продукта измерена (836.5, 10 ч); анализу `Гидроочистка.1.D15` 263.4 сут при пороге 80. T95 смеси 360.000148 °C сравнивается в целых °C и проходит |

Прежде (первый прогон после ADR-015/016) все четыре сценария заканчивались
отказом. Правила ADR-017 приняты командой после разбора: доказанное нарушение
по-прежнему блокирует всё, включая `hold`; неподтверждённый показатель
блокирует любое изменение, но не статус-кво; с пределом сравнивается значение в
разрешении лабораторного входа (T95 — 1 °C, плотность и ЦЧ — 0.1, сера не
округляется). Окна сценариев, пределы, пороги устаревания и допущения при этом
не менялись.

Это следствие данных, а не осторожность ради осторожности: продукт идёт на
~8.6 мг/кг при пределе 10, а ошибка прогноза 2.4 мг/кг. Чтобы система получила
право на экономическое действие, нужно уменьшить ошибку оценки серы (например,
ввести поточный анализатор ПАК с подтверждённой задержкой публикации), а не
ослаблять порог. Подробности — [ADR-013](docs/adr/013-blending-space.md).

- `evidence_type: backtested` — ошибка прогноза измерена на отложенной по
  времени истории. Это **не** доказательство эффекта управляющего действия и
  не утверждение о безопасности режима: backtest говорит о происхождении
  числа. Момент выдачи сценариев лежит внутри того же test-окна, по которому
  посчитана RMSE — сказать об этом надо самим.
- `evidence_type: simulated_unvalidated` — модельная оценка ещё не
  случавшегося действия. Симулятора установки нет, историей она не
  подтверждается по построению. Эту же подпись несёт и `hold`, пока текущий
  состав смеси модельный (ADR-013).

Оба числа подписаны в коде (`constraints.EVIDENCE_TYPES`) и в выводе сценария;
тест `tests/test_agents.py::TestOptimization` проверяет, что поле не пропущено
ни у одного кандидата.

Оркестратор сверяет пакет агента оптимизации не сам с собой, а с выводами
агентов качества и надёжности, собранными независимо: иначе подделать можно
обе копии сразу. На сценарии 4 это сработало содержательно — он отклонил
рекомендацию, в которой класс риска был взят с ближайшего горизонта, а порог с
худшего (ADR-010, §3б). Чего он проверить не может — перечислено в `limits`
его собственного вывода; главное: сам прогноз серы перепроверить неоткуда,
кроме как у агента качества.

Список — часть демонстрации, а не признание слабости: у каждой строки указано
основание, по которому её можно проверить.

| Единицы и физический масштаб `P8`, `T11`, `F19` не подтверждены; уставка показывается как безразмерный сигнал | [ADR-007](docs/adr/007-tag-map-inconsistent.md), `quality.json → data_confidence.*.units_confirmed = false` |

| Влияние изменения уставок P8/T11/F19 на T95 и цетановое число не моделируется: такие кандидаты отклоняются кодом `unmodelled_spec_effect`, а не оцениваются | [ADR-015](docs/adr/015-spec-t95-cetane.md), `optimization.json → rejection_codes` |

Для всех трёх компонент смеси не измеряется, поэтому модели смешения нет | [ADR-016](docs/adr/016-density-spec.md), «Последствия» |

## Непрерывная интеграция

`.github/workflows/tests.yml` прогоняет `pytest -q` на каждый push и pull
request, отдельными шагами — жёсткие ограничения и проверку `evidence_type`
(требование `CLAUDE.md`). Тесты, которым нужны крупные телеметрические CSV, в
CI пропускаются через `pytest.skip`, а не падают; отдельный шаг следит за тем,
чтобы пропуск не превратился в падение.

Проверено локально в чистом окружении (Python 3.11.9, pandas 3.0.5,
numpy 2.4.6, `pip install -e ".[dev]"`), при спрятанных `data/` и `build/` —
то есть ровно в том виде, в каком это увидит CI:

    240 passed, 9 skipped in 65.58s

Предыдущее измерение в тех же условиях — 176 passed, 9 skipped (Python 3.11.14);
рост даёт `tests/test_spec.py` и расширенные жёсткие проверки ([ADR-015](docs/adr/015-spec-t95-cetane.md)).

## Время, единицы и исправления формул

После обновления кода **перезапустите `python scripts/prepare_data.py`**:
старые CSV не содержат времени доступности и не подходят для новых проверок
признаков ЛИМС/ПАК.

- `timestamp` — время отбора пробы ЛИМС или измерения ПАК. Оно используется
  для лабораторных целей и разбиения по времени; не сдвигается на 4 часа.
- `available_at` — допуск в признаки: для ЛИМС `timestamp + 4h` (консервативная
  оценка без фактических публикаций), для ПАК `timestamp` (явное допущение,
  задержка не предоставлена). `availability_basis` хранит основание.
- `unit_declared` — исходная единица; `unit` — нормализованная;
  `unit_basis` — основание. Для ЛИМС единицы четырёх спорных показателей
  исправлены по названиям, температура записывается как `°C`. Массовая сера
  ПАК переводится из ppm в мг/кг с множителем 1; остальные ppm не переименовываются.
  `value` сохраняет исходное численное значение, `first_seen` — начало охвата.
- В `tag_map.csv` поле `description` для ВАК содержит формулу с поправками,
  `formula_original` — исходную запись XLSX, `formula_source` — источник
  (`source_xlsx` или `organizer_clarifications_2026-09-10`). Статус
  `corrected_unvalidated` означает исправленную запись без оценки точности;
  `original_unvalidated` — неисправленную и непроверенную. Статус
  `blocked_pipeline` у D15/T95 запрещает считать входы формулы разрешёнными:
  точка `Pipeline` по-прежнему не сопоставлена. Универсального вычислителя
  формул в пайплайне нет.

Пример получения истории, доступной в момент прогноза:

```python
import pandas as pd
from neftekod.splits import available_history, assert_no_leakage

history = pd.read_csv(
    "build/lims_pak_long.csv",
    parse_dates=["timestamp", "available_at", "first_seen"],
)
cutoff = pd.Timestamp("2025-06-01 12:00")
known = available_history(history, cutoff)
assert_no_leakage(known, cutoff)
```

Сохраняйте `source`, `timestamp` и `available_at` до проверки признаков.
На точной границе доступности значение уже разрешено. Неизвестное время или
отсутствие `available_at` у ЛИМС/ПАК вызывает ошибку, а не нулевую задержку.
`coverage.freshness` выбирает только доступные числовые значения и считает
возраст от отбора/измерения. Проверка прогноза на горизонте `h` использует
историю на момент выдачи, а не на будущий момент цели `cutoff + h`.
Часовой пояс источников общий, но не назван; UTC автоматически не назначается.
Времена в CSV записываются единообразно, включая полночь и микросекунды,
чтобы `parse_dates` восстанавливал все три временных поля.

  ГОСТ 32511-2013 / ГОСТ Р 52368 для К5.

  нормализует единицы и добавляет время доступности ЛИМС/ПАК. Исходники сохранены.
- Остаются открытыми точка `Pipeline`, единицы/масштабы КИП, суффикс `.Q` и

  организаторы оставили команде — они приняты по ГОСТ и помечены как параметры
