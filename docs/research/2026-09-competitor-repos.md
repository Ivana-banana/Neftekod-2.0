## Где мы сильнее (не трогать)

Разделение «не подтверждён / нарушен» (ADR-017), семь показателей ГОСТ с учётом
климатического сорта, adversarial-проверка в оркестраторе, `evidence_type`,
заморожённые сценарии с побайтовой воспроизводимостью, закрытый контур без
внешних API. У Zzzpize: отказ при ЛИМС старше 24 ч, одна сера в спецификации,
GigaChat как **внешний** API (в закрытом контуре не запустится), p05–p95 истории
в роли «безопасного диапазона» без пометки допущения.

## Проверенные находки

1. **Маркер 307.0 и дефекты телеметрии не фильтруются у нас в признаках.**
   ADR-007 фиксирует 307.0 у `F19`, но `features.py` отбрасывает только
   NaN/inf. На `data/242000_tags.csv`: `F19` = 307.0 в 2324 строках, это **одна
   непрерывная серия** (замороженный участок), плюс 7078 отрицательных значений;
   `P8` отрицательный в 191 строке. Это одна из правдоподобных причин провала
   телеметрической Ridge (RMSE 168–254), но не доказанная: проверять
   экспериментом. На АВТ 307.0 массово: `D10` почти всегда, `F26` — 71 тыс. строк.
2. **ПАК-сера плохо согласуется с ЛИМС.** 1459 пар «анализ ЛИМС
   `Гидроочистка.2` ↔ последний ПАК не старше 30 мин»: корреляция **0.22**,
   MAE 1.70 мг/кг, смещение ЛИМС−ПАК +0.25. При этом у ПАК есть инерция на
   коротком горизонте (автокорреляция на train: 0.94 за 10 мин, 0.56 за 1 ч,
   0.35 за 3 ч). Zzzpize и netoger учат модель на ПАК как на главной цели;
   для нас это означает: переходить на ПАК как цель **нельзя** (спецификация
   проверяется по ЛИМС), но прогноз ПАК на 0–3 ч может быть отдельной,
   явно подписанной величиной.
3. Верх шкалы ПАК около 20: 152 значения ≥ 19.9 мг/кг (netoger считает их
   цензурированными). У нас эта оговорка не зафиксирована.

## План внедрения

Порядок — по приоритетам CLAUDE.md: сначала данные и ограничения, UI в конце.
Сценарии заморожены (ADR-011): ни один пункт не меняет окна и не подбирается по
результату демо.

### P1. Детектор дефектов телеметрии (идея netoger `quality/detectors.py`)

**Сделано 2026-09-16, [ADR-018](../adr/018-telemetry-defects.md).** Маскируются
только `sentinel` и `frozen`: отрицательные значения оказались шумом нуля при
простое, а не невозможными величинами. Гипотеза «307.0 портит Ridge» не
подтвердилась — метрики не изменились. Ниже исходный план.

Что: модуль `src/neftekod/telemetry_defects.py` — маски `sentinel` (ровно 307.0),
`frozen` (серия одинаковых значений ≥ N шагов), `impossible` (отрицательные
расходы и давления, где физика запрещает), `clipped` (упор в верх шкалы).
Дефектное значение становится пропуском **до** выбора «последнего конечного»
в `features.py`, а его возраст растёт честно. Флаги попадают в вывод агентов
качества и надёжности.

Зачем: закрывает вход «аномальные данные» из ТЗ для телеметрии, а не только
для ЛИМС (сейчас ADR-014 покрывает только лабораторные значения).

Порядок:
1. Новый ADR-018: правила, N для `frozen`, список тегов, где отрицательное
   значение невозможно, с оговоркой, что единицы `F19`/`P8` не подтверждены
   (ADR-007). → verify: ADR в `docs/adr/`.
2. Тест на реальном фрагменте `242000_tags.csv` с серией 307.0 у `F19`
   (сначала падает). → verify: `pytest tests/test_telemetry_defects.py`.
3. Подключить в `features.py`, перегенерировать `forecast_report`. Если RMSE
   телеметрической Ridge изменится, записать это как результат, а не
   подгонку: лаг и alpha по-прежнему выбираются только на valid.
   → verify: `python scripts/evaluate_forecast.py`, diff отчёта.
4. Перепрогнать сценарии; изменение карточек объяснить в README.
   → verify: `python scripts/run_all_scenarios.py`, `md5sum -c` двух прогонов.

Риск: если фильтр изменит вердикт замороженного сценария, это нужно показать
как следствие исправления входа, а окно сценария не трогать.

### P2. Согласие ПАК ↔ ЛИМС как отдельная метрика доверия (находка 2)

Что: в `evaluate_forecast.py` добавить блок «ПАК против ЛИМС» (пары, корреляция,
MAE, смещение по train/test). Агент качества пишет в `data_confidence`, что
поточный анализатор слабо согласуется с лабораторией, и не подменяет ПАК
измерением ЛИМС.

Зачем: сильный аргумент на защите против подхода «учимся на ПАК». Число уже
посчитано, осталось закрепить его в воспроизводимом отчёте.

→ verify: тест на значение поля в `forecast_report`, строка в README.

### P3. Калиброванная верхняя оценка серы (Zzzpize `_conformal_radius`, netoger p90)

Что: сейчас запас выражается в единицах RMSE backtest. Добавить верхнюю
оценку `прогноз + q`, где q — квантиль 0.9 (или 0.95) абсолютной ошибки на
**valid**; покрытие проверить один раз на test. В отчёте указать долю
недопокрытия. Блок A (backtested); на контрфактические действия покрытие не
переносится (оговорка I04 у 4EPEn).

→ verify: тест «q считается только по valid»; покрытие на test в
`forecast_report.md`.

### P4. Разведка «оператор реагирует на анализ» (netoger `analyze_response.py`)

Что: скрипт считает для `P8`/`T11`/`F19` кросс-корреляцию в обе стороны:
тег(t−лаг)→сера и сера(t−лаг)→тег. Если обратная связь сильнее прямой, это
числовое подтверждение тезиса A7: регулятор выбирает действие по состоянию,
эффект уставок не идентифицируется. Сейчас этот тезис опирается только на слова
организаторов. Считать только на train и уже после P1, иначе 307.0 испортит
корреляции.

→ verify: `build/response_analysis.csv`, абзац в `docs/research/2026-09-offline-policy-evaluation.md`.

### P5. Трасса цикла с `decision_id` (Zzzpize `tracing/`)

Что: `build/scenario_*/trace.json` — упорядоченные шаги (роль, хэш входа,
краткий вывод, длительность). SQLite и сервер не нужны. Показывает
взаимодействие ролей на демо одним файлом (сценарий 4). Длительности не
детерминированы, поэтому держать их вне файлов, проверяемых `md5sum`, или не
записывать совсем.

→ verify: тест «шаги идут в порядке quality → reliability → optimization →
orchestrator, у всех один decision_id».

### P6. Текст объяснения от локальной LLM с guardrail на числа (Zzzpize `llm/guardrails.py`)

Что: необязательный слой. Карточку по-прежнему собирает шаблон; локальная
OpenAI-совместимая LLM (контур организаторов, до ~30B) может переформулировать
раздел «объяснение». Guardrail: любое число в тексте LLM должно быть в
`decision.json`, иначе текст отбрасывается и остаётся шаблонный. При
недоступной LLM тоже остаётся шаблон. LLM не участвует в вердикте.

Решение нужно от команды: окупается ли это на демо. Guardrail — ~70 строк и
тест, дёшево. GigaChat-клиент не переносить: это внешний API.

→ verify: тест с выдуманным числом отклоняет текст; прогон без LLM даёт
побайтово прежние карточки.

### P7. Просмотр сценариев (Zzzpize frontend) — последним

Что: один статический HTML, собираемый из `build/scenario_*/*.json`: выбор
сценария, свежесть источников, кандидаты с причиной отклонения, трасса P5.
Без Next.js/Docker. Делать только после P1–P5.

## Что сознательно не переносим

- **ПАК как главная цель прогноза** (Zzzpize, netoger): согласие с ЛИМС 0.22,
  спецификация проверяется по ЛИМС (находка 2).
- **LightGBM с monotone constraints как «причинная» модель эффекта** (netoger):
  монотонность задаёт знак, но не делает эффект идентифицируемым при обратной
  связи АСУ (A7). Можно рассмотреть позже только как ограничение формы с
  пометкой `simulated_unvalidated`.
- **Лимиты скорости изменения «2 °C за шаг»** (netoger): организаторы сказали,
  что ограничений скорости нет; выдуманный лимит был бы нормативом без источника.
- **Optuna-Парето и IsolationForest** (Zzzpize): 12 кандидатов перебираются
  полностью, стохастический поиск ломает побайтовую воспроизводимость;
  IsolationForest непрозрачнее правил P1.
- **Отказ при ЛИМС старше 24 ч** (Zzzpize): грубее наших порогов по показателям
  (48 ч для T95, 42 сут для ЦЧ).
- **GigaChat, Docker, Next.js**: внешний API и лишний вес для закрытого контура.
