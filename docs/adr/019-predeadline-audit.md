# ADR-019: исправления по итогам pre-deadline аудита

## Статус

**Принято 2026-09-22, реализовано.** Шесть независимых проверок (логика и
требования, ревью кода, adversarial-тестирование, производительность, взгляд
жюри, аудит submission) сошлись на одном наборе дефектов. Окна сценариев
(ADR-010, ADR-011), пределы, пороги устаревания, точка отсечения train/test
(ADR-006) и допущения блендинга (ADR-004, ADR-013) не менялись. Отчёт
backtest `build/forecast_report.csv` после правок побайтово совпадает с
прежним — модель прогноза не трогалась.

## Контекст: что нашёл аудит

1. **Измеренное нарушение серы не блокировало `hold`.** Прогноз — сдвинутый
   persistence `0.3·анализ + 0.7·8.6` (ADR-012), поэтому анализ 10.5 мг/кг
   давал прогноз 9.17 < 10, `check_sulfur` проходил, оркестратор утверждал
   сохранение режима с риском `high`. В test-периоде таких анализов 36 из 253;
   на sweep 872 моментов — 21 approved `hold` при измеренной сере > 10.
   Противоречило CLAUDE.md («доказанное нарушение блокирует всё»).
2. **Измеренное нарушение T95/плотности продукта маскировалось в «не
   подтверждён».** `spec.blend_*` возвращали `None`, если у любого компонента
   нет анализа — даже с долей 0.0074 %. Продукт с D15 = 850 и без анализа
   компонента получал `approved` с пометкой «плотность не подтверждена».
3. **`hold` отклонялся как «жёсткое нарушение», если текущая уставка на 0.2 %
   ширины вышла за p05–p95 train.** На sweep — 31–42 % моментов test-периода,
   из них большинство при допустимом режиме по агенту надёжности. Модельный
   диапазон выдавался за промышленный предел (против ТЗ, §4).
4. **Система структурно не могла рекомендовать действие.** Гейт «запас ≥
   backtest-RMSE» применялся к любому изменению, включая «убрать сернистый
   компонент», которое запас *увеличивает*; выбор среди допустимых шёл по
   минимальной стоимости, где `hold` выигрывал на 1e-5. Итог на всех окнах —
   `hold` либо отказ; в сценарии 2 `hold` с S = 9.74 утверждался, а вариант с
   S = 8.99 отклонялся как «недостаточный запас».
5. **Оркестратор обходился пакетом.** Без поля `blend_fractions` пересчёт
   смеси пропускался (`approved` при сере 1.0 против прогноза 9.3);
   показатели дешёвого компонента и «текущие доли» брались из самого пакета,
   который собирает агент оптимизации; `evidence_type` и `issue_time` не
   сверялись; `±inf` в пакете ронял оркестратор трейсбеком.
6. Мелкое: нефизичный анализ серы (−5) давал прогноз с риском `low`;
   залипший ПАК (одно число 7 суток в сценарии 3) показывался как «возраст
   0 ч»; останов установки (T11 = 27 при ~360) назывался «тяжёлым режимом»;
   причина отказа «ни один кандидат не прошёл» без деталей; оптимизатор и
   оркестратор брали прогноз с разных горизонтов (совпадало только потому, что
   baseline одинаков на всех горизонтах).

## Решение

1. **Измеренные показатели продукта сравниваются с пределами как факт.**
   `constraints.check_measured_product()` проверяет последний анализ серы и
   измеренные T95, ЦЧ, плотность. Агент качества кладёт результат в
   `measured_violations` и показатель `spec_indicators.sulfur`; при нарушении
   серы класс риска — `spec_violation_measured`. Агент оптимизации добавляет
   эти нарушения каждому кандидату кодом `measured_violation`; оркестратор
   пересчитывает их сам из вывода агента качества
   (`measured_product_within_spec`). Доказанное нарушение блокирует всё,
   включая `hold`.
2. **Компонент с нулевой долей не участвует в показателе смеси**
   (`spec._contributing`, то же правило в `orchestrator._component_values`).
   Его отсутствующий анализ больше не делает «убрать компонент» не
   сертифицируемым. Для компонентов с ненулевой долей правило ADR-017 не
   изменилось.
3. **Текущая уставка вне p05–p95 у статус-кво — предупреждение, а не
   нарушение.** Новый вид `constraints.MODEL_RANGE`; `blocking(status_quo=True)`
   его пропускает, оркестратор выводит предупреждение
   (`setpoints_within_applied_ranges` для статус-кво — пройдена с пометкой).
   Для любого изменения уставок диапазон остаётся жёстким.
4. **Гейт запаса и выбор среди допустимых.** Гейт «запас ≥ RMSE» не
   применяется к действию, не уменьшающему запас по сере относительно
   статус-кво: оно не рискованнее сохранения режима. Оркестратор проверяет то
   же правило, пересчитывая запас статус-кво по независимому текущему составу
   (`action_allowed_under_quality_risk`). Среди допустимых при риске `high`,
   `spec_violation_predicted` или `spec_violation_measured` выбирается
   наибольший запас по сере; при `moderate`/`low` — минимальная стоимость;
   тай-брейк — статус-кво. Это прямое применение ключевого принципа ТЗ:
   качество приоритетнее экономики.
5. **Контракт оркестратора ужесточён.** `blend_fractions` и `setpoints`
   обязательны (`validate_recommendation`). Источники `sources` теперь
   включают `components` (сера, T95, плотность дешёвого компонента, разрешённые
   из данных функцией `scenarios.independent_sources`, и его цетановое число
   из постановки) и `current_blend_fractions` (из `BlendingScenario`);
   оркестратор сверяет с ними вход (`component_values_match_sources`,
   `current_blend_fractions_match_sources`), проверяет физичность серы
   компонентов, совпадение `issue_time` с агентом качества и честность
   подписи `evidence_type` (`backtested` допустим только для статус-кво без
   модельной доли). Мусор в пакете (`inf`, список вместо строки, кривые
   границы диапазона) даёт `Violation`, а не traceback.
6. **Данные и сообщения.** Нефизичный последний анализ серы → отказ агента
   качества. Залипший ПАК (одно число ≥ 1 ч, порог ADR-018) помечается
   `data_confidence.pak_sulfur.frozen` и в карточке. T11 ниже 50 (простой по
   ADR-018) → `reliability.plant_stopped`, режим недопустим, фактор риска
   «установка остановлена». Причина отказа оптимизатора называет, почему не
   прошёл статус-кво. Сера сырья в единице, отличной от `% масс.`, → отказ, а
   не молчаливый множитель 10⁴. Оптимизатор и оркестратор берут прогноз с
   одного (худшего) горизонта. Карточка начинается с трёх строк «ситуация →
   действие → почему» и сравнивает действие со статус-кво.
7. **Производительность** (вывод побайтово тот же): `features`/`forecast`
   берут колонки массивами вместо `iloc` по строке; `run_all_scenarios.py`
   читает входные CSV один раз. evaluate 12.0 → 6.1 с, run_all 6.8 → 3.6 с.

## Последствия

- Сценарий 4 даёт утверждённое действие `adjust_blend`: снизить долю
  модельного прямогонного компонента с 0.0074 % до 0 — сера смеси 8.37 → 7.67
  мг/кг, T95/ЦЧ/плотность подтверждены свежими анализами продукта,
  `evidence_type: simulated_unvalidated`, состав по-прежнему модельный
  (ADR-004, `[MOCKED]`). Сценарии 1 и 2 остаются `hold` — там изменение
  блокирует неподтверждённый показатель (плотность 50 ч / ЦЧ 61 сут), и это
  правило ADR-017 сохранено. Сценарий 3 — отказ, теперь с названной причиной:
  установка остановлена, ЛИМС 179 ч, ПАК залип.
- Тестов стало 336 (было 322): добавлены измеренное нарушение серы и T95,
  выход уставки за модельный диапазон у статус-кво, приоритет запаса при
  риске `high`, подделка серы компонента и «текущих долей», пакет без состава,
  `backtested` у изменения, `inf` в пакете, нефизичный анализ.
- Что аудит нашёл и что **не** исправлено (сознательно, до дедлайна):
  Ridge по телеметрии обучается на цели с выбросами до 2120 мг/кг и на
  вырожденных age-признаках (RMSE 168–254 — артефакт метода, а не свойство
  данных); класс риска `high` в ~93 % моментов test-периода — порог в единицах
  RMSE неинформативен; ПАК не входит в прогноз, хотя корреляция ПАК–ЛИМС
  0.48 против −0.004 у соседних ЛИМС; АВТ не моделируется. Всё это записано в
  README, раздел «Что не реализовано».
