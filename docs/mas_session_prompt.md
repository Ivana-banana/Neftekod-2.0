## Задача этой сессии

Приоритет №1 из `CLAUDE.md`: **один сквозной прогон «данные → оценки агентов →
рекомендация»** на одном сценарии (устойчивый период без лишних действий).
Остальные 3 демо-сценария, полировка объяснимости и UI — не в этой сессии.

Это не «набросать каркас»: прогон должен реально считать на реальных данных и
заканчиваться либо конкретной рекомендацией, либо явным отказом с причиной.

## Чеклист (по порядку, каждый пункт — с проверкой)

1. **Признаки.** Модуль признаков поверх long-format + телеметрии. Каждая фича
   несёт явную точку отсечки (cutoff) и не смотрит вперёд.
   → verify: `tests/test_no_feature_leakage.py` — тест из `CLAUDE.md`, который
   проверяет, что ни одна фича не использует значения с
   `timestamp > prediction_time`. Сейчас в `splits.assert_no_leakage` есть только
   синтетическая проверка — нужна на настоящих признаках.
2. **Синхронизация источников по времени** (§2 ТЗ): merge телеметрии, ЛИМС и ПАК
   по времени с учётом возраста значения, а не по номеру строки.
   → verify: отдельный тест, что разная частота/охват источников не даёт ложный
   merge; возраст значения (`age_hours`) доезжает до признаков, а не теряется.
3. **Прогноз качества** (сера на выходе гидроочистки / показатели ДТ) на
   отложенном по времени тесте по ADR-006.
   → verify: метрика на test + baseline (persistence), обе цифры в отчёте. Если
   модель не бьёт baseline — так и написать, не подгонять.
4. **Агент качества** (`.claude/agents/quality.md`) — оценка риска выхода за
   спецификацию, в т.ч. сера ≤ 10 мг/кг.
   → verify: на выбранном окне выдаёт оценку с указанием, внутри или вне
   диапазона обучения находится вход.
5. **Агент надёжности** — тяжесть режима / риск для катализатора по прокси-
   признакам, допущения прокси описаны явно.
   → verify: прогон на том же окне; в выводе перечислены допущения.
6. **Агент оптимизации** — кандидатные воздействия, каждый вывод несёт
   машиночитаемое `evidence_type: backtested | simulated_unvalidated`.
   → verify: тест в CI, что поле не пропущено ни у одного вывода (требование
   `CLAUDE.md`).
7. **Оркестратор** — разрешает конфликт целей, проверяет финальную рекомендацию
   как adversarial-ревьюер: получает только (вход, рекомендация, применённые
   ограничения), без reasoning исполнителей. Не может независимо воспроизвести
   «ограничения соблюдены» → отклоняет.
   → verify: тест на кейс «рекомендация с лучшей экономикой, но нарушением» —
   отклонена; и на кейс «нет допустимого варианта» — возвращает явный отказ, а
   не натянутый результат.
8. **Сценарий 1 отдельным детерминированным скриптом** (`scripts/scenario_*.py`,
   фиксированный seed / frozen timestamp), вывод сохраняется в `build/`.
   → verify: два запуска подряд дают побайтово одинаковый вывод (`md5sum -c`).
9. **README** — как запустить сценарий одной командой.
   → verify: команда из README отрабатывает в чистом venv.

## Границы

- Жёсткие проверки не обходятся ради метрики нигде — включая «временно, чтобы
  прогон дошёл до конца». Stop-hook прогоняет `tests/test_hard_constraints.py`.
- Роли — отдельные subagent-файлы со своими промптами и инструментами, а не
  if/else внутри одного промпта. Взаимодействие между ними должно быть видно в
  коде.
- Не путать два числа: качество прогноза на отложенной истории (проверяемо) и
  оценка эффекта не случавшегося действия (не подтверждена историей). Оба
  подписаны в коде и в отчёте.
- Ничего не помечать «проверено»/«работает» без приложенного вывода команды.
- Упёрлось в ADR-001…003/005 — остановиться, оставить TODO со ссылкой на ADR,
  идти дальше. Не изобретать ответ за организаторов.
