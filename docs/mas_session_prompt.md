## Задача этой сессии

Приоритет №1 из `CLAUDE.md`: закончить **один сквозной прогон «данные → оценки
агентов → рекомендация»** на сценарии 1 (устойчивый период без лишних действий).
Остальные 3 демо-сценария, полировка объяснимости и UI — не в этой сессии.

Это не «набросать каркас»: прогон должен реально считать на реальных данных и
заканчиваться либо конкретной рекомендацией, либо явным отказом с причиной.

## Чеклист (по порядку, каждый пункт — с проверкой)

4. **Агент качества.** Прогнать роль `.claude/agents/quality.md` (через Agent /
   subagent_type "quality") на выбранном устойчивом окне реальных данных:
   оценка риска выхода за спецификацию (в т.ч. сера ≤ 10 мг/кг), с явным указанием
   in-range/out-of-range относительно обучающего диапазона.
   → verify: вывод сохранён (например, в `build/scenario_stable/quality.json`),
   в нём явно есть флаг in/out-of-training-range.
5. **Агент надёжности.** Тот же принцип: тяжесть режима / риск для оборудования
   по прокси-признакам, допущения прокси перечислены в выводе, а не только в коде.
   → verify: прогон на том же окне; допущения видны в сохранённом выводе.
6. **Агент оптимизации.** Кандидатные воздействия; каждый вывод несёт
   машиночитаемое `evidence_type: backtested | simulated_unvalidated` (см.
   `constraints.EVIDENCE_TYPES`).
   → verify: тест, что поле не пропущено ни у одного кандидата (можно расширить
   `tests/test_hard_constraints.py` или добавить рядом).
7. **Оркестратор.** Новый `.claude/agents/orchestrator.md`. Разрешает конфликт
   целей качества/надёжности/оптимизации и проверяет финальную рекомендацию как
   adversarial-ревьюер: получает только (вход, рекомендация, применённые
   ограничения), не reasoning исполнителей. Жёсткая часть проверки — не на
   доверии к LLM: оркестратор (агент или обвязывающий код вокруг него) обязан
   заново вызвать `constraints.validate_recommendation()` на фактических
   значениях рекомендации — независимо воспроизвести «ограничения соблюдены»,
   а не принять на слово агента оптимизации. Нет воспроизведения → отклонение.
   → verify: тест на кейс «рекомендация с лучшей экономикой, но с нарушением
   ограничения» — отклонена; тест на кейс «нет допустимого варианта» —
   возвращает явный отказ с причиной, а не натянутый результат.
8. **Сценарий 1 отдельным детерминированным скриптом**
   (`scripts/scenario_stable.py`, фиксированный seed / frozen timestamp),
   вывод сохраняется в `build/`.
   → verify: два запуска подряд дают побайтово одинаковый вывод (`md5sum -c`).
9. **README** — раздел «Как запустить сценарий 1» одной командой.
   → verify: команда из README отрабатывает в чистом venv.

## Границы

- Жёсткие проверки не обходятся ради метрики нигде — включая «временно, чтобы
  прогон дошёл до конца».
- Роли — отдельные subagent-файлы со своими промптами и инструментами, а не
  if/else внутри одного промпта. Взаимодействие между ними должно быть видно в
  коде и в сохранённых промежуточных выводах, а не только в финальном ответе.
- Не путать два числа: качество прогноза на отложенной истории (backtested,
  уже посчитано в ADR-008) и оценка эффекта не случавшегося действия
  (simulated_unvalidated). Оба подписаны в коде и в выводе сценария.
- Ничего не помечать «проверено»/«работает» без приложенного вывода команды.
- Упёрлось в ADR-001/003 — остановиться, оставить TODO со ссылкой на ADR, идти
  дальше. Не изобретать ответ за организаторов.
