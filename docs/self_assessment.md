# Самооценка по восьми критериям ТЗ

Дата: 2026-09-11. Состояние репозитория: коммит `66b9b47`, `master` синхронизирован
с `origin`. Проверяемые критерии — `docs/tz/tz_neftekod.md`, §6, «Что будет оцениваться».

Внешнего скоринга у задачи нет: ни лидерборда, ни платформы для загрузки решения, ни
автоматической метрики в материалах хакатона не упоминается (проверено поиском по
`docs/tz/*.md` и `README.md` — ноль совпадений по «дедлайн», «сдача», «загрузить»,
«жюри», «платформа»). Оценивают люди по восьми критериям на демонстрации, поэтому
единственная доступная нам проверка — прогон по этим критериям с приложенным выводом
команд. Ниже — он.

Правило `CLAUDE.md`: утверждение «работает» без вывода команды считается браком.
Поэтому у каждой строки указано, чем именно она подтверждена.

## Сводка

| № | Критерий | Оценка | Главный пробел |
|---|---|---|---|
| 1 | Работа с данными | сильно | нет отдельного детектора аномалий |
| 2 | Качество прогноза | **слабо** | выбранный baseline проигрывает константе |
| 3 | Мультиагентность | сильно | обмен виден в файлах, но не в UI |
| 4 | Оптимизация и безопасность | **средне** | система не может рекомендовать ни одного действия |
| 5 | Надёжность | средне | прокси-индекс без внешнего обоснования порога |
| 6 | Объяснимость | средне | 3 блока из 7 по §5 ТЗ закрыты полностью |
| 7 | Воспроизводимость | сильно | кросс-версионный детерминизм не доказан |
| 8 | Демонстрация | **слабо** | из четырёх сценариев готов один |

Три критерия из восьми — слабые или средние по причине, которую нельзя закрыть
косметикой. Они и должны быть предметом следующей сессии (`docs/demo_session_prompt.md`).

## 1. Работа с данными — сильно

Корректная синхронизация, отсутствие временной утечки, обработка пропусков и аномалий,
прозрачность единиц и признаков.

**Чем подтверждено.** `.venv/bin/python -m pytest -q` → `144 passed in 19.72s`. Из них
прямо по этому критерию:

| Файл | Тестов | Что закрывает |
|---|---|---|
| `tests/test_parse_lims_pak.py` | 25 | многоуровневые заголовки ЛИМС/ПАК на реальном фрагменте файла |
| `tests/test_time_split.py` | 11 | границы train/valid/test, `assert_no_leakage` |
| `tests/test_features.py` | 6 | `synchronize_features()` с явной точкой отсечки |
| `tests/test_tag_map.py` | 14 | соответствие CSV ↔ справочник КИП, поправки формул |
| `tests/test_coverage.py` | 5 | покрытие и свежесть показателей |
| `tests/test_telemetry_columns.py` | 4 | колонки телеметрии |

Синхронизация только по времени, не по номеру строки (ADR-009). ЛИМС доступен с
`sample_time + 4 ч`, это зашито в `available_at` и учитывается при построении признаков.
`build/coverage_report.md`: 56 показателей (ЛИМС 54, ПАК 2), период 2023-01-01…2026-08-11,
отдельно выписаны 14 показателей, появляющихся позже начала выгрузки более чем на 30 суток
— интерполяция через такой разрыв запрещена и не выполняется. Конфликты единиц (ADR-005)
сохранены в `build/unit_conflicts.csv` для аудита, исходные XLSX не менялись.

**Что не закрыто.** Отдельного детектора аномалий нет. Аномалии сейчас отсекаются
побочно — порогами устаревания (48 ч для ЛИМС, 1 ч для телеметрии) и границами p01–p99.
Это не одно и то же: выброс ЛИМС 2120 мг/кг внутри обучающей выборки ничем не помечен,
он просто не попадает в перцентильные полосы.

## 2. Качество прогноза — слабо

Это самая честная и самая неприятная строка отчёта.

**Что есть.** Backtest прогноза серы с учётом времени публикации, разделение fit/valid/test
зафиксировано до обучения (ADR-006), выбор лага и alpha — только на fit/valid, test
используется один раз. Все строки `build/forecast_report.md` несут `evidence_type: backtested`.

| Модель | test RMSE, мг/кг (h=0 / 1 / 2 / 3) | test R² (h=0) |
|---|---|---|
| persistence | 2.620 / 2.856 / 2.921 / 2.762 | −0.132 |
| ridge_telemetry | 168.2 / 143.1 / 213.8 / 254.5 | −4666 |

Телеметрическая Ridge проигрывает разгромно — это результат, а не недоработка, и он
корректно приводит к тому, что система отказывается рекомендовать изменение уставок.

**Найдено при этой самооценке — подтверждённый дефект выбора baseline.** Отрицательный R²
persistence означает, что модель хуже константы. Проверил: константа, равная медиане
обучающей выборки, выигрывает у persistence — и на valid, и на test, на всех горизонтах.

Выбор строго на `fit`, проверка на `valid` (test не трогался):

```
h=0 valid: persistence RMSE=  8.713 | fit_median(8.50) RMSE=  8.386
h=1 valid: persistence RMSE=  8.713 | fit_median(8.50) RMSE=  8.386
h=2 valid: persistence RMSE=  8.455 | fit_median(8.50) RMSE=  8.386
h=3 valid: persistence RMSE=  8.469 | fit_median(8.50) RMSE=  8.386

h=0 valid: persistence MAE= 2.453 | fit_median(8.50) MAE= 2.059
h=2 valid: persistence MAE= 2.331 | fit_median(8.50) MAE= 2.059
```

RMSE на valid задавлен выбросами (максимум цели там 120.0 при медиане 9.1), поэтому MAE
здесь информативнее — но константа выигрывает по обеим метрикам и на всех четырёх
горизонтах. То есть выбор был доступен честно, без подглядывания в test.

Подтверждение на test (не для выбора, только для оценки масштаба):

```
h=0 train_median const=   8.600  test RMSE=  2.483  MAE= 1.658  n=253
h=0 persistence               test RMSE=  2.620  MAE= 1.810  r2=-0.1323
h=2 persistence               test RMSE=  2.921  MAE= 1.916  r2=-0.4072
test: mean=8.282 std=2.467 min=0.100 max=20.300
```

**Почему это важно не только для метрики.** Число `2.921` (persistence на худшем горизонте)
используется как порог допустимости действия: запас по сере должен быть не меньше одной
backtest-RMSE (ADR-010, §3). С более точным baseline порог был бы `2.483`, и граница
допустимости действий сдвинулась бы. То есть дефект baseline влияет не на украшение
отчёта, а на то, какие действия система разрешает.

**Что не закрыто.** Baseline не заменён. Менять его сейчас, после того как я увидел
результат на test, — это ровно та подгонка, которую запрещает `CLAUDE.md`. Правильный
порядок: отобрать константный baseline на fit/valid (основание уже есть, см. вывод выше),
зафиксировать, и один раз проверить на test. Вынесено в `docs/demo_session_prompt.md`, п. 13.

Второе: тег `LIMS:Гидроочистка.1.Mass.Sulfur` — сера сырья гидроочистки, 132 значения
2023-01…2026-07, около 0.93 % масс. — не используется нигде в коде, хотя это первое звено
цепочки из примера самих организаторов («сера нефти → сера прямогонного ДТ → температура
на входе реактора и блендинг»).

## 3. Мультиагентность — сильно

Реальное разделение ролей и обмен информацией между агентами.

**Чем подтверждено.** Четыре роли — четыре отдельных модуля и четыре отдельных
subagent-промпта, не ветки в одном промпте:

```
src/neftekod/agents/{quality,reliability,optimization,orchestrator}.py
.claude/agents/{quality,reliability,optimization,orchestrator}.md
```

Обмен виден в сохранённых файлах, а не только в финальном ответе:
`build/scenario_stable/{quality,reliability,optimization,submission,decision}.json`.
Каждый следующий агент получает вывод предыдущего явной структурой данных.

Оркестратор — adversarial-ревьюер с обязательным аргументом `sources`. Он получает только
`input`, `recommendation`, `applied_constraints` и машиночитаемые отказы; лишний ключ на
любом уровне вложенности — исключение `_assert_contract()`. Жёсткая часть проверки не на
доверии к LLM: `decision.json` содержит 11 независимо воспроизведённых проверок, включая
повторный вызов `constraints.validate_recommendation()` на числах самой рекомендации,
пересчёт серы смеси по входу и сверку статус-кво по фактическим уставкам, а не по ярлыку
`action`.

Прогон ролей как subagent'ов оказался не декорацией: именно так нашлись четыре дыры в
самом оркестраторе (ADR-010, §6а) и ошибка с порогом по лучшему горизонту вместо худшего.

**Что не закрыто.** Взаимодействие читается в JSON, но на демонстрации его придётся
показывать открытыми файлами. Сценария 4 («полный цикл агентов») ещё нет.

## 4. Оптимизация и безопасность — средне

**Что сильно.** Жёсткие ограничения закрыты 29 тестами (`tests/test_hard_constraints.py`)
и Stop-hook'ом `.claude/hooks/check-hard-constraints.sh`, который нельзя обойти
формулировкой в чате. Приоритет качества над экономикой реализован не декларацией:
поле `expected_cost_saving_pct` внутри `recommendation` отвергается контрактом
оркестратора, то есть экономический аргумент физически не может попасть в проверяемый
пакет. Отказ — полноценный результат: есть вердикт `no_admissible_recommendation`.

Каждый отклонённый кандидат несёт машиночитаемый код причины из `REJECTION_CODES`:
`hard_constraint`, `insufficient_margin`, `unvalidated_effect_model`, `regime_inadmissible`.

**Что слабо, и это главное.** На текущих данных система не может рекомендовать **ни одного**
действия. В сценарии 1 отклонены все девять кандидатов: три варианта блендинга — жёстким
ограничением по сере (48.3 / 88.2 / 208.0 мг/кг против предела 10), шесть изменений
уставок — тем, что модель их эффекта проиграла persistence. Логика верная, но демонстрация,
где МАС четыре раза подряд говорит «ничего не меняем», не показывает умение «находить
допустимые компромиссы» — а это половина формулировки критерия.

## 5. Надёжность — средне

**Чем подтверждено.** Агент надёжности считает прокси-индекс тяжести режима и публикует
допущения в самом выводе, а не только в коде: `reliability.json` несёт `assumptions`,
`allowed_ranges_basis` с текстом «не подтверждённый промышленный предел» и список
`risk_factors`. Прокси сознательно не опирается на заявленный физический смысл
`P8/T11/F19`, потому что единицы не подтверждены (ADR-007).

В сценарии 1 фактор риска сработал содержательно: `F19` меняется со скоростью до 2.54
ширины рутинной полосы в час при том, что std за неделю остаётся 4.86 — короткий бросок,
невидимый в агрегате за окно. Скорость при этом **не** входит в индекс и ничего не
запрещает: организаторы прямо сказали, что ограничений скорости в задаче не задано, и
превращать наблюдение в норматив — значит придумать предел за них (ADR-010, §2а).

**Что не закрыто.** Порог допустимости `severity_index < 0.5` внешнего обоснования не
имеет. Он перечислен в `assumptions`, чтобы читатель не принял его за норматив, но
остаётся выбранным числом. Пробел занесён в `docs/research_brief_manus.md`, раздел 6.

## 6. Объяснимость — средне

ТЗ §5 задаёт семь блоков ответа оператору. Проверка по факту содержимого
`build/scenario_stable/recommendation.md`:

| Блок §5 | Состояние |
|---|---|
| Время и состояние | **частично** — момент выдачи есть, свежести ЛИМС/ПАК в карточке нет (она лежит в `quality.json`, `data_confidence`) |
| Проблема / риск | есть — риск `high`, предупреждение о запасе меньше одной RMSE |
| Предлагаемое действие | **частично** — действие названо, но нет формата «тег: текущее значение → рекомендуемое» |
| Ожидаемый эффект | **частично** — прогноз серы есть, влияния на выпуск и стоимостного прокси нет |
| Проверка ограничений | **частично** — в карточке прозой, список 11 проверок только в `decision.json` |
| Уверенность | **частично** — backtest-RMSE и запас в единицах RMSE есть, предупреждения о старых данных в карточке нет |
| Объяснение выбора | есть — все девять отклонённых кандидатов с причинами |

Полностью закрыты 3 блока из 7.

Сильная сторона, которую стоит показывать отдельно: раздел «Чего проверка не доказывает»
попадает в вывод машинно, из `orchestrator.REVIEW_LIMITS`, а не пишется в слайд руками.
Граница проверки — часть артефакта, а не устная оговорка.

**Отдельный дефект.** В карточке уставка выглядит как `P8 0.213335` и названа температурой.
Оператор такое прочитать не может. Это прямое следствие ADR-007 (единицы и масштабы КИП
не подтверждены), но в карточке оно должно быть помечено явно, а не показано как число.

## 7. Воспроизводимость — сильно

Решение запускается по инструкции и выдаёт повторяемый результат на одних и тех же данных.

**Чем подтверждено.** Повторный прогон сценария и сверка контрольных сумм:

```
build/scenario_stable/context.json: OK
build/scenario_stable/decision.json: OK
build/scenario_stable/optimization.json: OK
build/scenario_stable/quality.json: OK
build/scenario_stable/recommendation.md: OK
build/scenario_stable/reliability.json: OK
build/scenario_stable/submission.json: OK
```

7 файлов из 7. Детерминизм не случайный, а сконструированный: `agents/report.py`
округляет числа до 6 знаков, приводит `Timestamp` к строкам, `NaN`/`inf` к `null` и не
пишет в вывод время запуска.

README содержит раздел «Как запустить сценарий 1» с командой в одну строку; ранее он был
проверен в чистом venv (`pip install -e ".[dev]"`, 144 passed, `md5sum -c` 7/7 OK).

**Что не закрыто.** Чистый venv резолвил те же версии библиотек (Python 3.14.3,
pandas 3.0.5, numpy 2.5.3), поэтому доказан детерминизм при одинаковом окружении.
Побайтовая устойчивость к смене версии pandas/numpy не проверена и не заявляется.

## 8. Демонстрация — слабо

Целостный работающий прототип, а не набор несвязанных ноутбуков.

**Что есть.** Один сквозной прогон «данные → оценки агентов → рекомендация» на реальных
данных, детерминированный, с сохранёнными промежуточными выводами всех четырёх ролей.
Заглушечные входы честно печатают `[MOCKED: …]` в лог.

**Что не закрыто.** ТЗ §6 требует минимум четыре сценария. Готов один. Нет:
периода с риском ухудшения качества, ситуации с неполными/устаревшими/аномальными данными
(вся машинерия отказа написана и **ни разу не показана на реальных данных**), полного
цикла агентов отдельным сценарием. Нет единой команды на весь прогон, нет визуализации,
нет записанного скринкаста на случай сбоя на сцене.

## Что не реализовано и не проверено — основа для питча

По `CLAUDE.md` этот список — часть демонстрации, а не признание слабости.

| Пункт | Основание |
|---|---|
| Блендинг модельный: рецептур и спецификации в пакете нет; сера компонента 4000 мг/кг и цена 0.85 — допущения сценария | ADR-004, `[MOCKED: …]` в логе |
| Единицы и масштабы `P8/T11/F19` не подтверждены; в карточке уставка выглядит как `P8 0.213` | ADR-007, `data_confidence.units_confirmed = false` |
| `F19` ровно 307.0 в 2324 обучающих строках (1.48 %) — клиппинг, а не распределение | ADR-007, дополнение |
| Точка отбора `Pipeline` не резолвится в ЛИМС; T95 не используется | ADR-003, статус «Открыт» |
| Суффикс `.Q` организаторами не объяснён | ADR-001 |
| Момент выдачи сценария 1 (2026-02-04) лежит **внутри** test-окна, по которому посчитана backtest-RMSE | ADR-010, «Последствия» |
| `backtested` означает происхождение числа, а не безопасность режима: backtest измеряет ошибку прогноза, а не последствие удержания режима | ADR-010 |
| Дыра B оркестратора закрыта не полностью: сам прогноз серы перепроверить неоткуда | `orchestrator.REVIEW_LIMITS`, попадает в `decision.json` |
| Пороги 48 ч, 1 ч, 5 % ширины диапазона, классы риска и `severity_index < 0.5` — выбранные числа без внешнего обоснования | ADR-010, `assumptions` агентов |
| Выбранный baseline прогноза проигрывает константе — найдено при самооценке, не исправлено | этот документ, §2 |
| Эффект управляющего действия историей не подтверждается: симулятора нет | подтверждено организаторами |

## Что делать дальше

Порядок — по `CLAUDE.md` («при дефиците времени») и по тому, какие критерии слабы:

1. Сценарий 3 (отказ) — самый дешёвый и самый убедительный: машинерия готова, не показана.
2. Baseline прогноза: отобрать константу на fit/valid, зафиксировать, один раз проверить
   на test. Это чинит критерий 2 и уточняет порог допустимости действий.
3. Сценарий 2 плюс путь к действию, которое система имеет право рекомендовать
   (`LIMS:Гидроочистка.1.Mass.Sulfur`, массовый баланс блендинга) — чинит критерий 4.
4. Карточка оператора по всем семи блокам §5 с тестом на их наличие — чинит критерий 6.
5. Сценарий 4 и одна команда на весь прогон — чинит критерий 8.

Развёрнутые формулировки с проверками — `docs/demo_session_prompt.md`.

## Открытый вопрос к организаторам

Формат и дедлайн сдачи, нужен ли доступ к репозиторию, есть ли закрытый тестовый период
данных для финального прогона. Последнее важнее всего: если он есть, граница train/test
по ADR-006 должна быть согласована с ним. Ответ — в `docs/tz/organizer-clarifications.md`,
как и предыдущие уточнения.
